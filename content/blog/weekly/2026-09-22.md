Covers 2026-09-15 through 2026-09-22. `agent-fleet` and `editable-blog` had
no merged PRs, no open PRs, no new issues, and nothing in the journal for
either repo this window — everything below is `infra-bootstrap`.

## What shipped

[infra-bootstrap#244](https://github.com/MohammadBnei/infra-bootstrap/pull/244)
gave `common-app-chart` a `sharedSecrets.keys` option: a second
`InfisicalSecret` that syncs only named keys from a new `platform-commons`
project, instead of the old workaround of hand-duplicating one Redis
password into every project that needed it.
[#245](https://github.com/MohammadBnei/infra-bootstrap/pull/245) followed up
with the docs, and fixed a real gap while at it — the zot registry password
had only ever been recorded as a bcrypt hash, so onboarding a new build repo
meant hunting for the plaintext or rotating all four registry credentials.

The bigger story is
[has-journal](https://github.com/MohammadBnei/infra-bootstrap/pull/247).
It had been reverted the week before (#243) after landing on a branch mix-up
that pointed the Application at a `has-journal@master` with no `helm/`
directory at all — ArgoCD would have retried manifest generation forever.
#247 re-landed it, this time actually running `helm template` against the
real ApplicationSet values instead of just checking the files existed. But
the PR's own gate said **do not merge**: the OIDC machine identity for
`has-journal`'s CI had no auth method configured, so no image had ever
reached the registry, and merging first would leave the pod in
`ImagePullBackOff`. Mid-PR, the gate got smaller — has-journal's own
`InfisicalSecret` and `GH_TOKEN` requirement were removed by baking the
app's content into the image instead of `git fetch`-ing it at startup,
cutting the render from 10 objects to 8 and the blocker list from four items
to two. The last comment on the PR still shows the CI run failing at the
OIDC step. It merged anyway, same day.
[#248](https://github.com/MohammadBnei/infra-bootstrap/pull/248) then moved
the hostname to `has-journal.bnei.dev`, unrelated to the OIDC gate — an
operator-requested rename riding the Cloudflare wildcard from ADR-0038, no
DNS work needed.

[#249](https://github.com/MohammadBnei/infra-bootstrap/pull/249) moved
dream-analyst's image build off Docker Hub onto the in-cluster zot registry
via the self-hosted runner, while keeping `quality`/`e2e`/Trivy scan on
`ubuntu-latest` — the runner box runs buildah with no Docker daemon, and
`trivy-action` needs one.

## What was decided

ADR-0049, landed with #244: an app opting into `sharedSecrets` gets scoped
to named keys, but the scoping is env hygiene, not an access boundary — the
same Infisical project also holds the zot push credential, so an app could
in principle name that key and get registry-push access. Accepted, in
writing, as a homelab-scale risk.

## What stalled

Two of the three repos in scope: `agent-fleet` and `editable-blog`, flat
quiet, no PRs, no issues, nothing journaled. In `infra-bootstrap`,
has-journal itself is the stall worth naming even though the PR merged — the
OIDC identity `ci-has-journal` still had no auth method attached as of the
last visible run, which means the has-journal image may still not exist in
the registry despite the Application now being live under its new hostname.

## What it cost

[#246](https://github.com/MohammadBnei/infra-bootstrap/pull/246) went
looking for why the Infisical backend pod was restarting on every commit to
the repo, and the timing made #244 look guilty — its merge was followed by
a restart eight seconds later. Diffing the two ReplicaSets before writing
the fix showed the actual cause was `updatedAt`, a render timestamp the
Infisical chart stamps into the pod spec on every sync, restarting a
service every other app's secret sync depends on. The proof it wasn't #244
specifically: a docs-only commit (#245, zero chart changes) rolled the same
pod a minute later. The fix was `ignoreDifferences` on that one annotation,
scoped to the Infisical Deployment by name rather than a blanket rule,
since the same `updatedAt` idiom is a deliberate restart trigger everywhere
else. Cheap to fix once found; the expensive part was not shipping a fix
aimed at #244 on the strength of the timing alone.
